## 设计草案：共享环境(L1)灰度发布

> 现状：spec I 已定约束（R3：多版本只走灰度，主+灰度两档+流量比）。本节记录**怎么做**的思路，待实现时再细化为 spec 验收 + 技术文档。

**为什么 L1 适合先做**：L1 本就轻量跑多 agent（Claude Code 每 agent 一进程、OpenClaw 一个共享 Gateway 托多 agent），多挂一个灰度版本几乎零额外成本（L2 灰度要再开独占沙箱，重）。

**本质**：同一 agent 同时跑两版本（主 v_N + 灰度 v_N+1）+ **平台 router 分流**（不在运行时里做，框架无关）。

**三个关键设计点**：
1. **分流在平台 `service-chat` router**：每次对话决定打主还是灰度；运行时只需可寻址地同时存在两版本。
2. **按「会话」粘性，不能按「请求」**：多轮上下文只在一个实例上。新会话按流量% 掷骰选版本，同 session 后续轮固定。
3. **自描述 session_id 做粘性**：首轮选版本后，平台返回复合 id `v{ver}:{runtimeSid}`；下轮解析出版本直接路由。无中心粘性表、可水平扩展。

**L1 里"两个实例"怎么起**：
- Claude Code：主=进程 P1(v_N 工作目录, 端口①)；灰度=再起进程 P2(v_N+1, 端口②)。
- OpenClaw：主=共享 Gateway 里 agentId `a3`；灰度=同一 Gateway 再绑 `a3~canary`(v_N+1)。**不另起 Gateway**——"一个 Gateway 托多 agent"架构的红利。

**生命周期（声明式，用户表意图）**：开灰度(部署 v_N+1 + 流量%) → 调流量(改% 即生效，新会话按新比例、老会话不动) → 提升为主(v_N+1 接 100%、老主排空下线) → 回滚(杀灰度、秒级回主)。

**决策依据**：router 打**分版本指标**（错误率/时延/成本），同口径对比 → 用户决定提升/回滚。

**数据模型 + router 伪码**：
```
AgentDeployment {
  environment: shared
  primary: { version:3, target }              // CC=端口① / OpenClaw=agentId a3
  canary?: { version:4, trafficPct:10, target } // CC=端口② / OpenClaw=a3~canary
}
route(agentId, sessionId):
  dep = deployments[agentId]
  if not dep.canary: return dep.primary
  if sessionId 带版本前缀: return target_of(版本)        // 粘性：老会话照原版本
  pick = canary if rand()*100 < dep.canary.trafficPct else primary  // 新会话掷骰
  返回时把 "v{version}:{runtimeSid}" 作为 session_id 回客户端
```

**落地建议**：主流程改动小——发布加「灰度发布」入口（部署第二版本+流量%）；`service-chat` 加粘性路由；服务记录从单 `primary` 扩成 `primary + canary?`。**先做 Claude Code 的 L1 灰度**（两进程，最直观）跑通路由/粘性/提升/回滚，再接 OpenClaw 影子 agentId。配套前端：流量条 + 提升为主/回滚（mockup 已出，见对话记录）。
