# 运维排障

> 本地/部署运行时遇到的典型故障与定位修复手册。一个问题一节。

## Agent 报「Claude Code 未登录」，但其他 agent 正常

### 症状

某个 agent（最常见是通用助手 copilot）聊天返回：

> ⚠️ 运行环境的 Claude Code 未登录。请在**启动后端的终端**执行 `claude` 并 `/login`（或设置 ANTHROPIC_API_KEY），然后重启后端 / 重新发布该 Agent。

而同机其他 agent 能正常对话，手动在终端跑 `claude -p` 也正常。

### 根因

后端把每个已发布 agent（含 copilot）跑成常驻 `agent_runner.py` 子进程，用 **headless 方式**（`claude -p`，`stdin=DEVNULL`）调用 Claude Code。本机环境下 headless 的 claude **读不到 keychain 里的订阅登录**，必须靠环境变量里的有效 `ANTHROPIC_API_KEY`（在 `~/.zshrc` 里 export）。

子进程在 **被 Popen 的那一刻**就用 `os.environ.copy()` 固化了环境。而主后端重启时会**复用仍在监听的旧子进程**（见 `main.py` 的服务复活/对账逻辑），并不会刷新它们的环境。

于是：如果某个 agent 的服务子进程是在「环境里还没有有效 key」时启动的（key 为空或失效），它之后每次 `claude -p` 都没有可用凭据 → 报「未登录」。而 key 修好之后才（重）启动的 agent 拿到了有效 key，所以正常。

> 容易误判的两点：
> - **OpenClaw（qwen）agent 不走这个 key**，永远不受影响 → 造成「只有 Claude agent 挂」的错觉。
> - 手动在**交互终端**跑 `claude -p`（stdin 是 TTY）能成功，掩盖了「headless 必须有 key」这一前提。

### 定位

```bash
# 1) 列出所有 agent 服务子进程，逐个看工作目录与 key 长度
for PID in $(pgrep -f agent_runner.py); do
  AD=$(ps eww -p "$PID" | tr ' ' '\n' | grep '^AGENT_DIR='          | cut -d= -f2-)
  BK=$(ps eww -p "$PID" | tr ' ' '\n' | grep '^ANTHROPIC_API_KEY=' | cut -d= -f2-)
  echo "pid=$PID start=$(ps -o lstart= -p $PID) key_len=${#BK} dir=$AD"
done
# key_len=0 的就是陈旧进程；对照 ~/.zshrc 里的 key 即知有效与否
```

也可直接打活后端复现：
```bash
curl -s -X POST localhost:8000/api/copilot/chat -H 'X-User-Id: u0' \
  -H 'Content-Type: application/json' -d '{"message":"你好"}'
```

### 修复

让出问题的 agent 服务**停旧起新**，新进程会继承当前主后端的有效环境：

```bash
# copilot：应用自身的接口会停掉旧服务并重拉
curl -s -X POST localhost:8000/api/copilot/start -H 'X-User-Id: u0' \
  -H 'Content-Type: application/json' -d '{}'

# 或者：让全部 agent 服务重起（下次请求自愈拉起）
pkill -f agent_runner.py
```

### 防复发

- 本机 headless claude **必须**有有效 `ANTHROPIC_API_KEY`（订阅登录在 headless 下不可用）。
- **轮换 / 修复 key 后，光重启主后端不够**——它会复用带旧环境的子进程。务必让 agent 服务子进程也重启（`pkill -f agent_runner.py` 或逐个 `/api/.../start`）。
- 可选代码兜底（`backend/agent_runner.py`）：spawn `claude` 前若 `ANTHROPIC_API_KEY` 为空则记 warning，便于更快暴露「这个进程没拿到 key」。
