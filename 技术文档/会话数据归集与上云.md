# 会话数据归集与上云（会话 Tab 的技术方案）

> 配套产品 spec：[产品文档/specs/N-session-console.md](../产品文档/specs/N-session-console.md)、依赖 [M-agent-api.md](../产品文档/specs/M-agent-api.md)。
> 本文写 HOW（数据模型、归集通道、各隔离级别怎么把会话写回平台、查询与权限）；WHAT 与验收在 spec N。

## 0. 一句话结论

**会话 Tab 不需要"把数据从各沙箱搬上来"这件大工程**——因为平台后端在 M 阶段已经是所有对话的**中间人**：不论 Agent 跑在 L1/L2/L3，只要走平台统一 Session 接口，后端就**逐轮把 user/assistant 消息落进平台库 `sessions` 表**（见 `backend/main.py` `_session_event` / `_session_stream_gen` 对 `location=='cloud'` 与本地分支都调用 `_sess_append`）。

所以本方案的真实工作量是三块，按性价比排序：
1. **加「创建人」维度**（小）——让会话能按 Agent 创建人聚合、做可见性裁剪。**这是 MVP 的核心。**
2. **补元数据**（小）——会话上记录版本/环境/发起人/来源，供明细页展示。
3. **补「平台外直连」的旁路归集**（中，后续）——外部系统经稳定地址/网关直连 Agent 的会话不经平台接口，需要让网关/云端运行时把会话**异步回传**平台。

## 1. 现状盘点（已有 / 缺口）

| 能力 | 现状 | 出处 |
|---|---|---|
| 会话逐轮落库 | ✅ 已有，本地与云端(L2/L3)统一 | `_sess_append`、`_session_stream_gen` |
| L3 即用即弃明细不丢 | ✅ 明细在平台库，不随沙箱焚毁丢失 | 同上（平台侧持有） |
| 会话按「发起人 user」隔离 | ✅ 已有 | `sessions.user`，各查询 `WHERE user=?` |
| 会话按「Agent 创建人」聚合 | ❌ 缺：`agents` 表无 creator 列 | `agents` DDL 无 creator |
| 会话上的运行元数据 | ⚠️ 部分：有 `agent_ref`/`agent_version`/`environment_ref`，无 isolation/location/initiator 冗余 | `sessions` DDL |
| 平台外直连会话归集 | ❌ 缺：`service-chat`/网关直连不落 `sessions` | M「兼容旧端点」 |

## 2. 数据模型变更

### 2.1 `agents` 加创建人（必须）
```sql
ALTER TABLE agents ADD COLUMN creator TEXT;   -- 平滑加列，老数据回填为所属空间首个 owner / 'u0'
```
- 创建 Agent 时写入当前用户（`backend/main.py` 创建 Agent 处补 `creator=current_user`）。
- 与 `installed_skills.creator` 同款做法（项目里已有先例）。

### 2.2 `sessions` 冗余运行元数据（便于聚合查询与明细展示，避免 N 次回查）
```sql
ALTER TABLE sessions ADD COLUMN isolation TEXT;     -- L1/L2/L3，会话创建时按 environment/published 快照
ALTER TABLE sessions ADD COLUMN location  TEXT;     -- local / cloud
ALTER TABLE sessions ADD COLUMN initiator TEXT;     -- 对话发起人（= 旧 user 字段语义，显式命名）
ALTER TABLE sessions ADD COLUMN source    TEXT DEFAULT 'platform';  -- platform / gateway / cloud-callback
```
- `isolation`/`location`：在 `/api/sessions` 创建会话、或首轮落库时，从该 Agent 的 `published.isolation` + `services.location` 快照写入（钉死当时形态，后续 Agent 改环境不影响历史会话展示）。
- `initiator`：等于现有 `sessions.user`，新列只是语义显式化；可不迁移，查询时 `COALESCE`。
- `agent_version`：已存在，明细展示「调用时版本」。

> 说明：creator **不冗余进 sessions**，而是查询时 join `agents`——因为创建人是 Agent 的属性、应随 Agent 单点变更（未来支持转移时不必回刷历史会话）。

### 2.3 索引
```sql
CREATE INDEX IF NOT EXISTS idx_sessions_agent ON sessions(agent_ref);
CREATE INDEX IF NOT EXISTS idx_agents_creator ON agents(creator);
```

## 3. 各隔离级别的会话怎么归集（核心问题：数据如何上云/保存）

```
                         ┌─────────────────────────── 平台后端（中间人）───────────────────────────┐
 调用方 ──/api/sessions──▶│ _session_event → 落 user 一轮 → 转发下游 → 落 bot 一轮（_sess_append）    │
                         │                         ↓ 按 location 分支                                │
                         └───────────────┬──────────────────────────┬──────────────────────────────┘
                                         │ local                    │ cloud
                        L1 共享：本地进程/共享网关          L2 独立 / L3 即用即弃：AgentRun 云沙箱
                        （同机 _proxy 转发）               （_cloud().chat，以平台 sid 作会话亲和键）
                                         │                          │
                              对话明细 → 平台库 sessions      对话明细 → 平台库 sessions（后端回写，不依赖沙箱）
```

- **L1 共享**：Agent 在本地/共享网关，平台后端同机转发，`_sess_append` 落库。明细 100% 在平台库。
- **L2 独立**：Agent 在云端独占沙箱，平台后端用 `_cloud().chat(agent_id, message, sid)` 代理调用，**拿到 reply 后由后端落库**。沙箱只持有引擎续接态，**对话明细以平台库为准**。
- **L3 即用即弃**：同 L2，但沙箱「跑完即焚」。关键点：**明细不依赖沙箱存活**——后端在每轮 done 时已落库；沙箱销毁只丢引擎内存态（记忆需外置，本就是 L3 约定），不丢对话文本。
- 结论：**只要经平台统一 Session 接口，L1/L2/L3 的会话明细天然全在平台库**，会话 Tab 直接查库即可。这也是 spec N「全量归集 AC1/AC2」基本已就绪的原因。

### 3.1 唯一缺口：平台外「直连」会话（后续阶段）
外部系统按 M 的「稳定寻址」直接打 Agent 的网关/云端 endpoint（或走 `service-chat` 无状态端点），这类会话**不经 `/api/sessions`，平台库没有**。两条可选通道：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 网关旁路回传（推荐） | OpenClaw 网关 / AgentRun 运行时在每轮结束后，**异步**把 `{agent_id, session_key, turn}` POST 回平台一个内部归集端点 `POST /internal/sessions/ingest`；平台按 `(agent_id, session_key)` upsert 进 `sessions`，`source='gateway'` | 不改对外调用契约；需可靠投递（重试/幂等键）；运行时要带平台回传地址+凭证 |
| B. 统一强制走平台 | 对外只暴露 `/api/sessions`，网关直连仅内网可用 | 最干净，但牺牲 M「稳定寻址直连」的灵活性 |

推荐 A，并把它列为 spec N Phase 3。幂等键 = `(agent_id, session_key, turn_seq)`，避免重试重复落库；投递失败进本地队列重试，失败最坏是「该会话暂不出现」，不影响已归集会话（对应 AC4）。

## 4. 查询与权限（后端）

### 4.1 列表：`GET /api/sessions?scope=created`
```sql
-- scope=created：按「我是创建人」聚合 + copilot 本人会话；LEFT JOIN 以纳入无 agents 行的 copilot
SELECT s.id, s.title, s.agent_ref,
       COALESCE(a.name, '通用助手') AS agent_name,
       s.isolation, s.location, s.status, s.updated_at, s.initiator,
       json_array_length(s.messages) AS turns
FROM sessions s LEFT JOIN agents a ON a.id = s.agent_ref
WHERE (
        (a.creator = :me AND a.deleted = 0)               -- 我创建的 Agent 的会话
        OR (s.agent_ref = 'copilot' AND s.user = :me)     -- copilot 作特殊 Agent，本人可见
      )
  AND json_array_length(s.messages) >= 1                  -- “曾经活跃过”=至少 1 轮，空会话不计
  AND (:agent     IS NULL OR s.agent_ref = :agent)
  AND (:isolation IS NULL OR s.isolation = :isolation)
  AND (:q         IS NULL OR s.title LIKE '%'||:q||'%')
ORDER BY s.updated_at DESC
LIMIT :size OFFSET :page*:size;
```
- `scope=mine`（缺省）= 旧语义 `WHERE s.user = :me`，不破坏现有 Chat/Playground。
- copilot：`agent_ref='copilot'` 无 agents 行，用 `LEFT JOIN` + `COALESCE(name,'通用助手')` 纳入，按发起人本人可见。
- PlatformAdmin 全局可见（spec N 正式要求，本期不做）：未来对 admin 去掉 creator 谓词即可。

### 4.2 明细：`GET /api/sessions/{id}` 鉴权
```python
# 可见 ⟺ 我是该会话所属 Agent 的创建人；或 copilot 本人会话；或我是 PlatformAdmin（本期 False）
visible = (
    (agent and agent['creator'] == me)                      # 创建人维度
    or (session['agent_ref'] == 'copilot' and session['user'] == me)  # copilot 本人
    or is_platform_admin(me)                                # ⬜后续，本期恒 False
)
if not visible:
    raise HTTPException(404, "会话不存在")   # 不泄露存在性
```
返回体在原 `messages`（**完整内容、不脱敏**——创建人可见全文）基础上补 `agentName/agentVersion/isolation/location/initiator/createdAt/source`。

## 7. 产品决策（已确认 ✅ / 待定 ❓）
- ✅ 内容隐私：创建人可见他人使用其 Agent 的**完整内容、不脱敏**。
- ✅ copilot 作为**特殊 Agent 进**会话 Tab（按发起人本人可见）。
- ✅「曾经活跃过」=**至少 1 轮**，空会话不计入。
- ✅ 平台管理员可越创建人边界看全部——**写为 spec N 正式要求，本期不实现**（admin 谓词预留）。
- ❓ 创建人转移/继承策略（当前固定初始创建人，转移留后续）。
