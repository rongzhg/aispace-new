# 架构设计（后端 / 运行模式）

> 现阶段以**前端 demo**表达产品逻辑；只有前端说不清的逻辑才考虑做后端。本文件是做后端时的技术参考，记录已讨论的方向，非本期必做。

## 1. 两种 Agent 运行模式（核心）

| 模式 | 特征 | 运行载体 |
|---|---|---|
| 短周期 | 单 session、短时、无状态、不需记忆 | **阿里云 Function Compute (FC)** 一次性执行 |
| 长周期 | 单 session 多轮对话、需状态与记忆 | **用户本机当沙箱**：本地常驻 runtime 跑 |

要点：FC 短命无状态，适合请求-响应；长会话/有记忆的不塞进 FC。

## 2. 控制面 / 数据面

- **控制面**（管元数据与编排）：FC + 数据库。存 Agent 配置、版本快照、项目空间、成员、路由（某 Agent 属哪种模式、连到哪台机器）。
- **数据面**（真正跑 Agent）：
  - 短模式 → FC 一次性运行（可用容器镜像跑无头 Claude Code：`claude -p` / Agent SDK，做有边界的单次任务）。
  - 长模式 → 用户本机 runtime（见下）。

## 3. 长模式：本机 runtime 接入

- 本机跑一个**常驻小客户端（runtime/daemon）**，启动时用 token 向平台**主动建出站长连接**（WebSocket）——避免云端反向连接被 NAT/防火墙挡住。
- 平台把发给该 Agent 的对话顺连接推给本机；本机跑 Agent、流式回传；**session 状态与记忆存本地磁盘**。
- 路由需 **session affinity**：同一会话粘在那台机器。
- 在线要求：本机离线则该长 Agent 暂停（适合"工作时的多轮会话"，非 7×24 全自动托管）。
- 需要：跨平台客户端、心跳、自动重连、token 鉴权。

> 这与 GitHub self-hosted runner、各类本地 agent 工具的连接方式一致。

## 4. 数据存储

- 本地开发：SQLite 即可。
- 部署到 FC：**不要**依赖本地库（实例临时、多实例并发会分叉）。
  - 低并发单实例 demo：可用挂载 NAS 的 SQLite。
  - 稳妥：**Tablestore**（serverless，demo 规模近免费）；要关系型用 RDS/PolarDB。

## 5. 模型调用

- **DashScope / 百炼（含伏渊 yufeng-vl）**：阿里云原生，从 FC 调最顺，demo 优先。
- **Anthropic / OpenAI**：需出公网 + API key，国内网络可能受限；长模式由本机出网调用更自然。
- 密钥用 FC 环境变量 / KMS，不硬编码。

## 6. 接口契约

按 `完成定义-DoD.md`：接口先定 **OpenAPI 契约**，前后端基于同一份并行 vibe coding。字段命名照 `../产品文档/glossary.md`。

## 7. demo 边界

- "每用户长跑沙箱/本机 runtime"是真正的平台工程；demo 阶段可先只跑短试跑，长模式用本机起一个 runtime 演示即可。

## 8. 发布即起服务（每 Agent 一服务）— 已落地初版

点「发布」时（先选运行环境），后端不只是写工作目录，还**为该 Agent 启动一个常驻服务进程**，暴露 HTTP `/chat`。

- **运行器**：`backend/agent_runner.py`（FastAPI），cwd=该 Agent 的发布工作目录（含 `CLAUDE.md`），按其模型跑 `claude`，提供 `/chat`、`/health`。
- **编排**：`backend/main.py` 在 publish 时分配端口（9100+）、`subprocess.Popen` 拉起运行器、写入内存服务注册表 `SERVICES`，发布响应返回 `service_url`。
- **调用**：Chat/Playground 经后端代理 `POST /api/agents/{id}/service-chat` → 该 Agent 服务的 `/chat`（规避跨域、便于鉴权）。
- **两个状态分清**：发布状态（已发布 vN，持久于 `published` 表）vs 服务运行态（运行中/已停止 + url，在 `SERVICES` 注册表）。

### 运维 UI 设计（复用，不单独建页）
- 服务是"已发布 Agent 的运行态"，归属 Agent → 复用 **Agent 列表 + 详情**：
  - 列表徽标：「已发布 vN · 运行中/已停止」。
  - 详情「运行服务」区：状态 + URL + 端口 + 启动/停止/重启。
- **不做**单独的"服务列表页"；仅当需要跨 Agent/跨用户的全局运维总览时，才作为**平台管理员**视图后续追加。

### 版本策略（本地单实例 / FC 版本随请求）
两类 Agent 的运行/版本策略不同，刻意分开以保持简单：

- **本地 Agent**：长驻**单实例**——同一时刻只活一个版本（= 已发布版本）。重发布新版本 = **停旧起新**（已实现：`SERVICES` 记录带 `version`，换版本则替换实例/端口）。不做灰度/多版本并跑；回滚 = 重发旧版本。
- **FC Agent**（云端短任务，无状态）：**版本随请求**——调用时传 version，就用该版本配置跑一次，天然支持任意版本，无需"多实例"。

**两个零成本预留**（保证将来要多版本/灰度时是加法、不返工）：
1. 服务记录带 `version`（不只按 agentId）——"单实例"只是当前只跑一个，模型能表达多个。
2. 调用一律走稳定路径 `POST /api/agents/{id}/service-chat`（后端代理），**不暴露端口**；外部不依赖裸地址。

> 灰度/AB/流量切分本质是"多用户在线 serving"的需求——它落在 FC 那侧（版本随请求即可），本地侧坚持单实例最省心。需要别名路由（prod/canary）时再在 FC/网关层加。
> 注意：`session_id` 绑定在实例上，本地换版本后旧 session 不能 resume。

### 本机 → 云端映射
- 本机：后端用子进程起每个 Agent 的服务（端口区分）。⚠ 后端勿带 `--reload`（会扰乱子进程）；`SERVICES` 在内存，后端重启会遗留孤儿进程 → 用「停止所有 Agent 服务」(`POST /api/services/stop-all`，pkill 兜底) 清理后重发布。
- 云端正式环境：每个 Agent 服务跑在**每用户 sandbox** 内（容器/进程），平台维护服务注册与路由；依赖隔离按 `单sandbox多agent验证.md`（per-agent venv，必要时容器）。
- 运维 UI：服务是"已发布 Agent 的运行态"，复用 **列表徽标（运行中/已停止）+ 详情「运行服务」区（状态/URL/启停）**；跨 Agent/跨用户的全局运维总览作为**平台管理员**视图后续再加（不提前建页）。

## 9. 通用 Agent（Copilot）= Claude Code + 平台工具（MCP）
- `backend/mcp_server.py` 暴露平台操作为 MCP 工具（list/create/publish agent、空间…）。

## 10. 运行时隔离级别（正式环境）

Agent/会话的运行时隔离是一条"隔离强度 ↔ 成本"的连续谱，可**按 agent 甚至按操作**配置，默认从粗到细按需升级：

| 级别 | 范围 | 何时用 |
|---|---|---|
| **L0 每用户沙箱** | 租户边界（必备） | 永远——跨用户**绝不**共享沙箱 |
| **L1 用户内多 agent 共享沙箱** | 同一用户的多个 agent 共用 | 默认、最省 |
| **L2 每 agent 一沙箱** | 一个 agent 一个容器 | 重要 agent、有依赖冲突、需更强隔离 |
| **L3 每 session 一沙箱** | 一次会话一个容器，跑完即焚 | 跑不可信/任意代码、最强隔离 |

**选级别的判定维度**（命中任一就升级，别只凭"重要"）：是否跑不可信/任意代码、爆炸半径、资源占用、合规要求，以及**系统级**依赖冲突（不同 OS 包/运行时版本）。

> ⚠ **"依赖隔离"不是升级 L2 的理由。** 普通 pip/npm 库依赖在 L1 共享沙箱里用 **per-agent venv / node_modules** 就能隔离（见 `单sandbox多agent验证.md`：jinja2 3.0.3 与 3.1.4 在同沙箱共存）。L2 真正多出来的是**爆炸半径**——故障、资源、安全：一个 agent 崩溃 / 吃满资源 / 被攻破时**不波及**同沙箱其他 agent；外加能装 L1 搞不定的系统级依赖。

### 用户侧文案（发布弹窗用意图语言，L 级别只作小标）

不要把 "L1/L2/L3" 直接抛给用户选——那是工程词汇、易选错。发布时呈现为：

| 用户看到 | 一句话 | 适合 | 底层 |
|---|---|---|---|
| **共享环境**（默认） | 和你其他 agent 共用一个沙箱，启动快、最省（各自库依赖仍隔离） | 多数 agent | L1 |
| **独立环境** | 独占沙箱：崩溃 / 资源占用 / 被攻破都不波及别人；需要系统级特殊依赖时也用它 | 重要 agent、强隔离 | L2 |
| **即用即弃** | 每次会话开全新沙箱、跑完即销毁，隔离最强 | 跑不可信代码 | L3 |

- **默认"共享环境"**，放进"高级"折叠区，让多数人不用动它。
- 选 **即用即弃** 时当场提示："环境跑完即销毁，长期记忆需外置（持久卷/记忆库），否则会话结束即丢"。

**每个"沙箱"应隔离的维度**：进程、文件系统、网络出口、依赖、密钥/凭证、资源配额。

**成本与生命周期**：越细越贵——L2/L3 需 **warm pool 预热 + 空闲回收 + 编排**。特别地：**L3 是临时的，长期记忆必须外置**（持久卷/记忆库），否则会话结束即丢。

### 隔离级别 × 框架（运行时矩阵）

隔离级别和框架是**正交**两维。同一隔离级别下，不同框架的"怎么跑"不一样：

| 级别 | Claude Code | OpenClaw |
|---|---|---|
| L1 单沙箱多 agent | 每 agent 一个轻量进程（`claude -p`，按需起） | **一个 Gateway 托多个 agent**（`agents.list` + bindings，按 agentId 路由）——**不要**每 agent 起一个 Gateway |
| L2 每 agent 一沙箱 | 每沙箱跑该 agent 的进程 | 每沙箱一个 Gateway（或 `sandbox.scope:"agent"` 给单 agent 单容器） |
| L3 每 session 一沙箱 | 临时沙箱起一次性会话进程 | per-session workspace / 临时 Gateway，跑完即焚 |

**适配器差异（关键，别照搬）**：

- **Claude Code 适配器** = "每 agent 一进程"（轻量、一次性，天然隔离）——我们现在的 `agent_runner` 即是。
- **OpenClaw 适配器** ≠ 每 agent 一进程。OpenClaw 是常驻 Gateway，应"**沙箱里跑一个 Gateway，把多个 agent 配进 `agents.list`**"，平台 `/chat` 带 `agentId` 路由（经 `message send`/RPC）。在一个共享沙箱里塞多个 Gateway 是反模式（最重又没真隔离）。

> 本地 demo 只到 L1（单机共享）；Claude Code 走每 agent 进程，OpenClaw 走共享 Gateway。
>
> **demo 现状（已落地）**：框架可插拔编排在 `main.py` `_start_service` 按 `framework` 分派——
> - `CLAUDE_CODE` → `backend/agent_runner.py`：每 agent 一进程（`claude -p`），各占一端口。
> - `OPENCLAW` → `backend/openclaw_gateway.py`：**一个共享 Gateway 托多个 agent**。发布即 `_ensure_gateway`（懒启动，一个隔离域一个 Gateway）+ `_bind_openclaw_agent` 把 agent 热绑进 `agents.list`（`POST /agents`，不重启）；对话经 `POST /chat {agent_id,…}` 按 agentId 路由；停服 `DELETE /agents/{id}` 解绑，最后一个解绑后 Gateway 停止。多个 OpenClaw agent 在 `GET /api/services` 各占一条，但 `url/port` 同指共享 Gateway 且带 `gateway:true`。
> - **已接通真实 OpenClaw（`engine: openclaw`，非 mock）**：发布 → `openclaw agents add <id> --workspace <dir>` 注册 + 人设同步（role+agent→`SOUL.md`、user→`USER.md`）；对话 → `openclaw agent --agent <id> -m <msg> --json` 按 agentId 路由（回复取 `payloads[0].text`，会话取 `meta.agentMeta.sessionId`）；停服 → `openclaw agents delete`。本机未装 `openclaw` 时回退 mock。完整接口/排障见 openclaw对接.md。
> - 可观测：`GET /api/gateway` 返回共享 Gateway 运行态 + 当前托管的 agents.list。

## 10.5 通用 Agent（Copilot）运行时定位

Chat 入口背后的「通用助手」是一个**平台自带、常驻**的编排者 agent（区别于用户自建 agent）。它和隔离级别是**两条正交的轴**，别混：

```
轴① 编排运行时        决定：skill 怎么挂、MCP 工具怎么调、多 session 怎么并发
轴② 隔离级别 L0–L3     决定：爆炸半径、租户边界
```

**隔离定位 = L0，不是 L2。** copilot 一个 agent 服务所有用户，若给它 L2（每 agent 一沙箱）= 全员共用一个 copilot 沙箱，反而踩穿 L0 租户边界。正确做法：**copilot 常驻在每用户自己的 L0 沙箱里**（该沙箱同时是开发 + 该用户 agent 的运行时）。它自身**不跑不可信代码**（需求澄清在本地多轮对话 + 调受信工具；真正「跑某个 agent」是另起的已发布服务，落到那个 agent 自己的 L1/L2/L3），所以 copilot 不需要 L2/L3。

- **租户边界**：由 L0 沙箱 + **API 层鉴权**双重兜底（每个平台操作工具调用带用户身份校验），不是靠给每次会话开沙箱。
- **多 session 并发**：编排运行时的事（多个 agent loop / asyncio 任务），与隔离级别无关。
- **防资源挤占**：配额 / 限流，不必升 L2。

### copilot 路由与寻址（一个用户一个，ws 作上下文）

每用户一个 copilot（住其 L0 沙箱），N 个用户 N 个 copilot——但**对外只有一条路由**，靠身份解析分流：

```
              对所有人相同的一条路由
  用户X ─┐  POST {后端}/api/copilot/chat[/stream]   ┌─► X 的 copilot 端点（X 的沙箱）
  用户Y ─┼─►  后端从鉴权拿到 user ──► 注册表解析 ──┼─► Y 的 copilot 端点（Y 的沙箱）
  用户Z ─┘     body 带 ws（当前空间，仅上下文）       └─► Z 的 copilot 端点（Z 的沙箱）
```

设计要点：
- **实例键 = 用户（不是 ws、更不是端口）**。一个用户的所有空间**共用一个 copilot**；「当前操作哪个空间」作为**每请求上下文**注入消息（`[当前工作空间: <id>]`），copilot 据此给工具传 `workspace_id`。`system_md` 不再硬编码 ws。
- **不需要固定端口**。稳定的是「身份 → 端点」映射 + 后端入口；端口是动态内部细节（重启对账 / 自愈保证映射常新，见 接口契约「稳定寻址」）。
- **身份既是路由键又是隔离边界**：X 的请求只会解析到 X 的沙箱，天然租户隔离。
- **会话粘性自动成立**：一用户一实例 → 多轮 `session_id` 永远落同一 copilot，不串实例。
- **解析器可插拔（与隔离级别正交）**：

  | 部署 | 路由键 | `_resolve_copilot_endpoint(user)` 解析到 |
  |---|---|---|
  | demo 单机 | user | 本机子进程端口（懒启动 + 自愈 + 落库对账） |
  | 生产 L0 沙箱 | user | 该用户沙箱内 copilot 端点（沙箱编排器 provision 时登记、回收时删） |

> **demo 现状（已落地）**：copilot 实例键 `copilot-<user>`（`copilot.copilot_id(user)`）；`/api/copilot/{start,status,stop,chat,chat/stream}` 从 `X-User-Id` 头取用户（缺省 `u0`，生产换真实鉴权），`ws` 作 query 上下文经 `_ctx_message` 注入；`_resolve_copilot_endpoint(user)` 为身份→端点解析钩子（local 已实现，sandbox 预留）。验证：同一路由下 `u0`/`alice` 解析到各自独立 copilot；一个用户跨 w1/w2 复用同一实例。

**两个扩展点（单 agent 编排都支持，copilot 与用户 agent 复用同一套绑定）：**

| 扩展点 | 物化到工作目录 | Claude Code 怎么用 |
|---|---|---|
| 加 **skill** | `.claude/skills/<name>/SKILL.md`（上传包则解包整棵树） | 启动时扫描自动发现，懒加载（只读 frontmatter 的 description） |
| 加 **MCP** | `.mcp.json`（`mcpServers`，env 用 `${VAR}` 展开、凭证不入库） | `--mcp-config` 加载，把每个 server 的工具挂进编排 |

出厂**内置集**（copilot 的 `agent-creator` / `skill-creator` / `requirement-clarify` 三个 skill + `aispace` platform-ops MCP）与用户从**市场安装**集，在「构建工作目录」时**合并**。

**需求澄清 → 落地（sink 抽象）**：copilot 用 `requirement-clarify` 技能多轮追问收敛成 EARS 需求，确认后调 `submit_requirement` 工具落地。落地是**可插拔 sink**——demo 用 `FileSink`（写需求收件箱文件「暂存到文档」），正式上线设 `AISPACE_REQ_WEBHOOK` 切到 `HttpSink`（POST 给外部系统）。同一接口换实现，**澄清逻辑一行不动**。

### 作用域（scope）：平台全局 vs 空间私有

「所有工作空间可访问的 skill/MCP」与「copilot 放哪」是同一件事：用一个 **scope 维度**统一。

- `scope=platform`：平台全局，**所有空间可见可绑**，住保留系统空间 `__system__`（不是租户，是平台系统目录，对用户隐藏、仅管理员可改）。
- `scope=workspace`：空间私有（现状，市场安装/注册进某空间）。
- **有效集 = platform ∪ workspace −（本空间禁用的全局项）**，同 id 时 workspace 覆盖 platform。
- **可见(scope) ≠ 挂载(binding)**：scope 决定"能不能用"，binding（agent 的 skills/tools 字段）决定"挂不挂"。全局项不强制挂到每个 agent；`default_on=1` 的全局项才"copilot 默认挂载"。
- copilot 的三内置 skill + platform-ops MCP 就是第一批 `platform` 行；copilot 本身登记为 `scope=platform` 的 agent 模板。后续加全局能力 = 加 `platform` 行，零新机制。
- 安全红线：全局定义不焊死 ws / 凭证；`{ws_id}`、身份、密钥在**实例化**时绑当前用户（`${AISPACE_API}` 等 env 运行时展开）。

> **demo 现状（已落地）**：
> - 作用域：`installed_skills/installed_mcp/agents` 加 `scope`(+`default_on`)；保留空间 `__system__`（`/api/workspaces` 隐藏）；`_effective_rows` 解析有效集；`/api/skills` `/api/tools` 返回 platform∪ws（标 `scope`/`disabled`）；`ws_disabled` + `/api/scope/{kind}/{id}/disable|enable` 按空间禁用全局项；`/api/platform/*` 管理全局项；`_seed_platform` 把 copilot 三 skill + platform-ops + copilot agent 沉淀为 platform 行。
> - 单 agent 挂载：`main.py` `_materialize_skills` / `_materialize_mcp` 在发布时物化绑定的 skill/MCP（按有效集解析，可绑平台全局）；`agent_runner.py` 检测到 `.mcp.json` 即 `--mcp-config` 加载（无 `.mcp.json` 的普通 agent 不受影响）。
> - copilot：`backend/copilot.py` 写 `CLAUDE.md`（编排者人设）+ 三个内置 skill + platform-ops `.mcp.json`；`POST /api/copilot/start|chat|stop`、`GET /api/copilot/status`（懒启动）。运行时复用 `_start_service`（`claude -p`）。
> - platform-ops MCP：`backend/mcp_server.py`（`list/create_agent`、`publish`、`create_workspace`、`submit_requirement` 等）。
> - 本 demo 用 Claude Code 当编排运行时跑通；正式版可换 **Agent SDK 内嵌后端**——运行时外壳变，skill/MCP 定义与 sink 抽象不变。

## 10.6 Managed Agent 标准模型（Agent + Environment + Session）

对标业内 Managed Agents（[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/sessions)、[Qoder Cloud Agents](https://qoder.com/en/cloud-agents)，Gemini 亦同）——三家收敛到同一模式,我们以此为标准对齐：

```
Agent        版本化配置(模型/prompt/工具/MCP)                     —— 已有
Environment  运行环境/沙箱(隔离级别、网络、依赖),session 创建时绑定  —— Phase 2 一等资源化
Session      有状态实例 = (Agent + Environment)                    —— Phase 1 已统一
             服务端持有历史(事件日志);按 id 寻址;事件驱动状态机
```

**标准的关键属性**:① Session 服务端有状态、对话历史归后端;② 事件驱动(`POST /sessions/{id}/events` 发 `user.message`),非纯请求响应;③ SSE 流式;④ 可中断恢复(event-log replay / wake);⑤ 单一 `session_id` 语义(续接 token 内部);⑥ Agent/Environment/Session 解耦。

> **逐接口差异对照**（vs Claude Managed Agents，15 端点逐条）见 ../产品文档/specs/M-agent-api.md「逐接口对齐对照」。一句话：L1/L2/L3 是隔离级别（Environment 属性）非三套协议，共用一套 Session API；外形已对齐，差距在事件驱动深度（两步生命周期 / 独立流端点 / 事件日志 / `interrupt`·`tool_confirmation`·`status`·`usage` 富事件）。

**我们的对齐路线（每阶段可独立上线,旧端点留适配器不破坏上游）:**

| 阶段 | 内容 | 状态 |
|---|---|---|
| **Phase 1** | **统一 Session**:`sessions` 表 + `/api/sessions/*`(create/events[/stream]/get/list/put/delete);copilot 与普通 agent **都**有服务端历史;`session_id` 单一语义;旧 `/api/copilot/*`、`/service-chat` 转薄适配器 | ✅ 已落地 |
| **Phase 2** | **Environment 一等资源**:`environments` 表;session/发布绑 `environment_id`;把"在哪跑/隔多严"从 agent 定义拆出 | ⬜ |
| **Phase 3** | **事件状态机**:`events` 富事件(`message.delta`/`status`/`tool.use`/`tool.confirm`/异步任务);派发(需求澄清/vibe-coding)落进同一条 session 事件流 | ⬜ |
| **Phase 4** | **对齐细节**:session 状态机(creating/running/idle/archived)、archive、**vaults**(MCP 凭证托管)、session 创建时**钉 agent 版本** | ⬜ |

> **Phase 1 现状（已落地）**:`main.py` 统一会话层——`sessions` 表(从旧 `copilot_sessions` 幂等迁移);`_sess_resolve/_sess_append/_sess_set_token` + `_session_downstream`(copilot→按用户解析 / 普通 agent→SERVICES 服务,均等就绪) + `_session_stream_gen`(转发 SSE 边解析边落库);`POST /api/sessions`、`/api/sessions/{id}/events[/stream]`、`GET/PUT/DELETE`;`SessionEventIn` 兼容 `{message}` 与标准 `{events:[user.message]}`。验证:普通 agent `a1` 经 `/api/sessions` 拿到服务端历史;copilot 经旧适配器仍工作且会话按 `agent_ref` 正确分域。
